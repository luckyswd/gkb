# Справочные материалы изменения

## Откат всей выкладки

Метка `pre-redesign` стоит на коммите `2d6ca94` — состояние сайта до редизайна.
Редизайн влит в `main` merge-коммитом `78dfab2`. Выкладка автоматическая, поэтому
откат — тоже коммит в `main`:

```bash
git revert -m 1 78dfab2 && git push origin main
```

Раннер соберёт прежнюю тему и зальёт её сам. Проверка, что откат полный:
`git diff pre-redesign main -- wp-app/` должен быть пустым. После отката так же
нужно очистить кеш WP-Optimize.

Контент товаров не менялся, откатывать в базе нечего; снимки «до» лежат в
`content-before/` на случай, если правка контента будет сделана позже.

## `screens-before/` — задача 1.2

22 снимка (11 страниц × ширины 1440px и 390px, JPEG, суммарно ~7 МБ):
главная, каталог, категория «Газовые котлы», товар «Житомир-Турбо»,
о производстве, прайс-лист, где купить, документация, контакты, вход, 404.

**Как снимать узкие ширины.** У headless Chrome минимальная ширина окна —
500px, поэтому `--window-size=390` даёт страницу, свёрстанную на 500px и
обрезанную до 390. Это выглядит как переполнение, которого на самом деле нет.
Снимки на 390px делаются через центрированный iframe шириной 390px внутри окна
500px с последующей обрезкой — этим занимается `shot.sh`. Снимки «после»
нужно делать тем же способом, иначе пары будут несравнимы.

## Опорные классы для содержимого вкладок

Проставляются вручную в визуальном редакторе (задача 10). Базовое оформление
работает и без них — классы нужны там, где важна точность макета.

| Класс | На чём | Что даёт |
|---|---|---|
| `gkb-steps` | обёртка над блоками преимуществ | отступы между блоками, запускает счётчик |
| `gkb-step` | один блок преимущества | номер `01`, `02`, … рисует CSS-счётчик, руками не проставлять |
| `gkb-accent` | врезка | светло-красная подложка, скругление |
| `gkb-specs` | зарезервирован под таблицу характеристик | — |
| `gkb-note` | сноска под таблицей | мелкий серый текст |

**Что увидит тот, кто будет размечать.** Содержимое вкладок — плоская
последовательность `<p>`: заголовки обёрнуты в `<strong>`, между блоками стоят
пустышки `<p>&nbsp;</p>` и `<p>.</p>`, которыми в старой вёрстке делали отступы.
В новом оформлении отступы задаёт CSS, и одинокая точка станет видна как точка.
Удалять ли эти пустышки — вопрос к владельцу сайта: формально это изменение
текста, хотя смысла в них нет. Базовое оформление работает и с ними.

**Важно про `gkb-step`:** картинку нужно ставить **первой** внутри блока —
тогда текст обтекает её справа, как в макете. Если картинка стоит последней,
она окажется под текстом и прижмётся вправо: вёрстка не сломается, но
side-by-side не получится. Таблицы оборачивать не нужно — это делает тема.

## Известная проблема доступности, оставленная как в макете

Граница поля ввода (`--gkb-border-strong`, `#d6d7da`) даёт к белой карточке
контраст 1.44:1 при норме WCAG 1.4.11 — 3:1 для границ элементов управления.
Фон поля отличается от карточки всего на 1.07:1, поэтому поле на белом почти
не читается как поле. Спецификация этого не требует, а заметное усиление
границы меняет вид формы, поэтому оставлено как в макете. Чинится заменой
`--gkb-border-strong` на цвет примерно `#949699`.

## Что нашлось уже на боевом сайте

Три вещи всплыли только после выкладки — на стенде их было не видно.

1. **`partials/product-cards.php`** — файл от другого проекта с короткими
   тегами `<? endif; ?>`. При выключенном `short_open_tag` блоки `if` не
   закрывались, `php -l` падал. Новая проверка синтаксиса в CI остановила
   первую выкладку до заливки по FTP — сайт не пострадал. Теги исправлены.
2. **Таблица прайс-листа** на телефоне занимала 1275px в контейнере 375px и
   обрезалась: страница не прокручивается вбок, поэтому колонки с ценами были
   недоступны. Обёртка таблиц теперь применяется ко всему содержимому из
   редактора, а не только ко вкладке характеристик. Такая же таблица есть во
   вкладке «Комплектация» у 11 товаров из 13.
3. **Логотип шире, чем в макете** (180px против ~60px), из-за чего меню из
   шести пунктов переносилось на вторую строку. Поиск возвращён в брусок
   категорий, логотип ограничен по ширине.

## Сломанная склейка JS на боевом сайте

WP-Optimize склеивает все скрипты в один файл
`wp-content/cache/wpo-minify/<метка>/assets/wpo-minify-footer-<хеш>.min.js`.
После выкладки этот файл приходит **обрезанным** — он обрывается на полуслове
внутри кода Swiper:

```
...(Array.isArray(i)?i:i.split;
```

Из-за этого в консоли `Uncaught SyntaxError: Unexpected token ';'`,
`typeof Swiper === "undefined"`, и **весь скрипт сайта не работает**:
мобильное меню, переключатель языка, вкладки товара, галерея, подсказки
к иконкам, аккордеон на «Где купить».

Собранный темой файл при этом корректен — `node --check dist/js/*.js`
проходит без ошибок. Ломает именно склейка.

**Чем закончилось:** при следующей выкладке склейка пересобралась целой
(164 КБ, `node --check` проходит), скрипты на сайте работают. То есть обрыв
был разовым сбоем генерации, но он может повториться на любой выкладке —
и тогда сайт снова останется без JS без единой ошибки в собственном коде.

**Что сделать, чтобы не повторялось:** в WP-Optimize → Minify → JavaScript отключить склейку и
минификацию JS. Тема и так отдаёт один уже минифицированный файл с
уникальным именем на каждую сборку, так что плагину там нечего улучшать.
Как вариант — очистить кеш минификации и проверить, соберётся ли файл
целиком; но при двух плагинах минификации сразу (WP-Optimize и
W3 Total Cache) это будет повторяться.

Проверка:

```bash
curl -s https://gazkotelbel.com/ | grep -oE 'wpo-minify-footer-[a-f0-9]+\.min\.js' | head -1
```

— взять этот адрес и прогнать через `node --check`.

## Кеш на боевом сайте — обязательный шаг при выкладке

Страницы отдаются с кешем WP-Optimize: стили и скрипты склеены в
`wp-content/cache/wpo-minify/<метка>/...`, а HTML, судя по поведению языка,
тоже кешируется. Имена файлов в `dist/` при каждой сборке случайны, поэтому
склейка стилей пересоберётся сама — а вот закешированный HTML продолжит
ссылаться на старую склейку. **После выкладки кеш нужно очистить** в админке
(WP-Optimize → Cache → Purge cache), иначе посетители увидят старую страницу.
Доступа к админке у меня нет, этот шаг за владельцем сайта.

Как проверить, что выложилось: на странице должна быть ссылка на новую склейку,
а в разметке — классы `gkb-header__`, `gkb-footer__`, `gkb-card`.

## Найденные проблемы (вне объёма этого изменения)

**Кеш страниц товаров игнорирует язык.** На боевом сайте `/products/<slug>/`
отдаётся из кеша по URL. Посетитель, переключивший сайт на английский,
продолжает видеть русское содержимое карточки товара — или наоборот, если в
кеш попала английская версия. Проверяется так:

```bash
curl -s -b "lang=en" "https://gazkotelbel.com/products/zhytomyr-turbo/" | grep -c "Write to us"
curl -s -b "lang=en" "https://gazkotelbel.com/products/zhytomyr-turbo/?x=1" | grep -c "Write to us"
```

Первая команда вернёт `0`, вторая — ненулевое число. Редизайн эту проблему не
создаёт и не чинит: язык хранится в куке, а кеш о ней не знает. Чинится либо
исключением страниц товаров из кеша, либо переносом языка в URL.
