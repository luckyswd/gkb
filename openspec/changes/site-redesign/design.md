## Context

Мотивация и объём — в [proposal.md](proposal.md). Здесь — только то, что определяет подход.

Боевая тема `wp-app/wp-content/themes/gkb-theme` — классическая WordPress-тема: PHP-шаблоны, сборка на Gulp (`main.scss` → `dist/css/style<случайное число>.min.css`, `main.js` с `//=include` → `dist/js/build<случайное число>-min.js`), подключение стилей и скриптов перебором файлов в `dist/`.

Выкладка автоматическая: `.github/workflows/main.yml` по пушу в `main` ставит зависимости, выполняет `npx gulp build` и заливает каталог `wp-app/` по FTP на боевой сервер. Каталог `dist/` в репозитории игнорируется (`.gitignore`) — он существует только локально и в раннере. Отсюда два следствия: пуш в `main` равен выкладке на боевой сайт, а собранные файлы нельзя проверить по diff — только по результату сборки. Весь контент сайта лежит в полях ACF; страницы собираются редактором из ACF-блоков (`modules/*`). Язык переключается кукой `lang`, значения берутся из групп `ru_language` / `en_language` (`Helpers::get_field_multi_lang`).

Макеты в папке `Редизайн сайта Gazkotelbel/` — это `.dc.html`: формат дизайн-документа с собственным рантаймом (`<dc-import>`, `<sc-for>`, `class Component extends DCLogic`) и тестовыми данными в `gkb-data.js`. Это эталон внешнего вида и поведения, а не исходники: ни одну строку оттуда нельзя перенести в тему как есть. Данные в `gkb-data.js` захардкожены — в теме те же сущности приходят из ACF.

Две детали текущей реализации, на которые опирается план:

- Иконки характеристик — спрайты 64×32 из двух состояний. `.product_icon` шириной 32px с `overflow: hidden` показывает левую половину, по наведению `justify-content: flex-end` показывает правую. Макет воспроизводит ровно это, только через анимированный `translateX(-32px)`.
- Подпись к иконке уже выводится (`.product_text`, скрыта `visibility: hidden`, показывается по наведению), а `assets/js/partials/product-card.js` вручную считает её смещение влево.

## Goals / Non-Goals

**Goals:**

- Один слой токенов, из которого берут цвет, шрифт, скругление и тень все страницы — включая контент из визуального редактора.
- Внешний вид макетов на боевых данных: произвольное число товаров, изображения разных пропорций, две языковые версии, пустые поля.
- Правки идут поверх существующих шаблонов и ACF — без переноса контента и без смены URL.
- Редактор продолжает собирать страницы теми же блоками и полями.

**Non-Goals:**

- Переход на блочную тему (FSE), Gutenberg-шаблоны, сборщик вместо Gulp, фронтенд-фреймворк.
- Изменение структуры полей ACF, типов записей, таксономий, механики языка и авторизации.
- Переработка административной части, счётчика Яндекс.Метрики, настроек Contact Form 7.
- Новый поиск: поле в шапке продолжает отправлять запрос на `/catalog?search=`.

## Decisions

### Д1. Переоформляем существующую тему, а не делаем новую

**Решение:** правим `gkb-theme` на месте: шаблоны и SCSS переписываются, структура темы остаётся.

**Альтернативы:** новая классическая тема рядом; блочная тема (FSE); headless.

**Почему:** все 26 групп ACF привязаны к этой теме через `acf-json`, страницы собраны из её блоков, модули тянут поля по именам. Любая новая тема означает перепривязку групп и пересборку каждой страницы руками, при нулевой выгоде — визуальный результат тот же.

### Д2. Токены — CSS-переменные на `:root`, SCSS остаётся только для сборки

**Решение:** все цвета, радиусы, тени, шаги шкалы отступов и типографики объявляются один раз в `assets/style/global/_tokens.scss` как `--gkb-*` на `:root`. SCSS-переменные остаются только там, где нужны вычисления на этапе сборки (брейкпоинты, миксины).

**Альтернатива:** оставить SCSS-переменные, как сейчас в `variables.scss`.

**Почему:** содержимое вкладок товара приходит из визуального редактора и стилизуется селекторами по элементам — переменные времени выполнения дают там те же цвета без дублирования значений. Плюс это единственное место, где задаются запасные значения (Д3).

### Д3. oklch с запасным значением в hex, без новых зависимостей сборки

**Решение:** каждый цветовой токен объявляется дважды подряд:

```scss
--gkb-accent: #2f8a3e;
--gkb-accent: oklch(0.62 0.17 147);
```

Браузер без поддержки `oklch()` не понимает вторую строку и оставляет первую.

**Альтернативы:** PostCSS-плагин, генерирующий запасные значения; отказ от oklch в пользу hex.

**Почему:** в сборке сейчас только Gulp и `gulp-autoprefixer`, новый плагин тянет за собой обновление цепочки. Приём работает без инструментов. Плата — дисциплина: цвет объявляется ровно один раз, в `_tokens.scss`; нигде в коде не должно быть `oklch()` или hex вне этого файла. Это проверяется поиском по `assets/style`.

### Д4. Inter размещаем у себя, Google Fonts не подключаем

**Решение:** четыре начертания Inter (400/500/600/700) в формате woff2 с подмножествами latin + cyrillic кладутся в `assets/fonts/Inter/`, подключаются через `@font-face` с `font-display: swap`. Roboto удаляется.

**Альтернатива:** `<link>` на `fonts.googleapis.com`, как в макетах.

**Почему:** аудитория сайта — Беларусь и Россия, где Google Fonts отдаётся медленно и нестабильно; это ещё и сторонний запрос на каждой странице. Тема уже самостоятельно отдаёт Roboto — механизм и задача `fonts` в gulpfile есть, меняется только содержимое папки.

### Д5. Табы каталога — обычные ссылки, страницы рендерит сервер

**Решение:** лента сегментов в каталоге — это `<a>` на существующие URL (`/catalog` и `/product-category/<slug>/`). Активный сегмент определяется на сервере по текущему запросу. Никакой клиентской фильтрации.

**Альтернатива:** как в макете — отдать все товары разом и фильтровать на клиенте.

**Почему:** URL категорий проиндексированы, `taxonomy-product-category.php` уже их отдаёт, а спецификация `catalog-visibility` требует, чтобы скрытого раздела не было в разметке, а не только на экране. Визуально результат неотличим: сегмент выделяется тем же стилем.

**Счётчики** берутся из того же запроса, что и листинг (`Helpers::getProductsByCategory`), а не отдельным подсчётом термов — иначе снятый с публикации товар попадёт в счётчик, хотя в сетке его нет.

### Д6. Текучие размеры на `clamp()` от ширины окна, без контейнерных запросов

**Решение:** `clamp()` с `vw` в качестве переменной части; контейнерные запросы не используются. Новый брейкпоинт 900px добавляется к существующим миксинам, остальные сохраняются.

**Альтернатива:** повторить макет буквально — `container-type: inline-size` и единицы `cqw`.

**Почему:** в макете контейнерные запросы нужны, чтобы один и тот же компонент рисовался в рамке 1440px и в рамке 390px на одном холсте. На боевом сайте контейнер — это сама страница, поэтому `cqw` и `vw` дают одинаковый результат при более простой поддержке. 900px — порог, на котором макет переключается между десктопной и мобильной шапкой (`isMobile = w < 900`).

### Д7. Иконки характеристик: оставляем спрайт, подпись превращаем в подсказку

**Решение:** сохраняем приём со спрайтом 64×32 (загруженные картинки устроены именно так) и анимируем сдвиг через `transform` вместо переключения `justify-content`. Подпись `.product_text` позиционируется по центру над иконкой средствами CSS; ручной расчёт смещения в `assets/js/partials/product-card.js` удаляется. Показ подсказки — по `:hover`, по `:focus-within` и по нажатию на сенсорном экране; обработчик нажатия отменяет переход по ссылке карточки.

**Альтернатива:** отказаться от спрайта и рисовать иконку одним состоянием.

**Почему:** спрайты уже загружены редактором для всех товаров — отказ от второго состояния обесценил бы готовый материал. Подсказка сейчас видна только с мышью: на телефоне посетитель не узнаёт значение иконки, а это и есть главная претензия к текущему каталогу.

### Д8. Форма обратной связи переезжает в подвал, якорь сохраняется

**Решение:** контейнер формы остаётся с `id="feedback-form"`, но выводится в потоке подвала. Кнопки, которые сейчас открывают модальное окно (`data-fancybox data-src="#feedback-form"`), становятся ссылками `href="#feedback-form"` с плавной прокруткой. Разметка самой формы (Contact Form 7) не меняется.

**Почему:** id сохраняется — значит не ломаются ссылки из контента, который редактор мог проставить руками. CF7 не трогаем: его обработка, валидация и письма остаются прежними.

**Следствие:** Fancybox после этого, возможно, не нужен вовсе. Перед удалением из `main.js` проверяется поиском по теме и по контенту, не используется ли `data-fancybox` где-то ещё (например, в WYSIWYG-полях). Если не используется — библиотека и её стили выбрасываются из сборки.

### Д9. Содержимое вкладок: селекторы по элементам плюс небольшой набор классов

**Решение:** два уровня.

1. **Базовый.** Всё внутри контейнеров вкладок стилизуется селекторами по элементам: `h2`–`h4`, `p`, `ul`/`ol`, `img`, `table`, `strong`. Этого достаточно, чтобы любой товар — в том числе не тронутый руками — выглядел опрятно.
2. **Опорный.** Пять классов, которые проставляются вручную в контенте: `gkb-steps` (список нумерованных блоков), `gkb-step` (блок «номер + заголовок + текст + картинка»), `gkb-accent` (врезка на светло-красной подложке), `gkb-specs` (таблица характеристик), `gkb-note` (сноска под таблицей). Номера блоков рисует CSS-счётчик, вручную их проставлять не нужно.

**Альтернативы:** только CSS без правки контента (тогда нумерованные блоки и врезка недостижимы); перенос в структурированные поля ACF (отклонён — это пересборка контента 13 товаров в двух языках).

**Почему:** базовый уровень страхует от небрежной разметки и новых товаров; опорный даёт точность макета там, где она видна. Классы добавляются в выпадающий список стилей редактора (плагин TinyMCE Advanced уже стоит) — чтобы редактор мог применять их сам, не заходя в HTML.

### Д10. Таблицы оборачиваются на выводе, а не в редакторе

**Решение:** поле `specifications` перед выводом пропускается через небольшой фильтр в PHP, который оборачивает каждую `<table>` в прокручиваемый контейнер. Липкая первая колонка — `position: sticky` на первых ячейках строки.

**Альтернатива:** просить редактора оборачивать таблицы в `div` руками.

**Почему:** редактор работает в визуальном режиме и обёртку будет терять при каждой правке. Фильтр делает это один раз и для всех товаров сразу, включая будущие.

### Д11. Галерея и слайдер остаются на Swiper

**Решение:** Swiper сохраняется и для галереи товара, и для промо-блока главной. Счётчик «1 / 5» — это штатная пагинация Swiper в режиме `fraction`. Миниатюры — существующий режим `thumbs`, меняется только расположение: вертикально слева от 900px, горизонтально под изображением ниже.

**Альтернатива:** написать галерею вручную, раз в макете нет перелистывания свайпом.

**Почему:** Swiper уже в сборке, умеет касания, миниатюры и клавиатуру. Писать это заново — риск без выигрыша. Промо-блок остаётся слайдером ещё и потому, что спецификация `homepage-promo-slider` описывает поведение при нескольких слайдах: редактор должен иметь возможность добавить баннер.

### Д12. Порядок правки: сначала токены и общие элементы, потом страницы

**Решение:** SCSS переписывается не по страницам, а слоями: токены → сброс и базовая типографика → общие элементы (кнопки, поля, табы, таблицы, карточки-контейнеры, хлебные крошки) → шапка и подвал → страницы. Каждая страница опирается только на готовый слой ниже.

**Почему:** иначе общие элементы соберутся из частных случаев трёх страниц и начнут расходиться на четвёртой. Это же определяет порядок задач в [tasks.md](tasks.md).

## Risks / Trade-offs

- **Два стилевых файла на странице.** `register_styles_scripts()` подключает всё, что найдёт в `dist/`, а имена файлов при сборке случайны. Если старый артефакт не удалён — на странице окажутся две версии стилей. → Локально задача `build` начинается с `clearDist`. На сервере удаление старых файлов зависит от того, что FTP-действие помнит их в своём state-файле; после первой выкладки нужно убедиться, что в `dist/` на сервере остался один файл стилей и один скриптов, и при необходимости удалить лишние вручную.
- **oklch без запасного значения.** Один пропущенный цвет — и в старом Safari блок станет прозрачным или чёрным. → Все цвета объявляются только в `_tokens.scss`; перед выкладкой — поиск по `assets/style` на `oklch(` и `#` вне этого файла.
- **Правка контента 13 товаров ломает цифры.** Ручная расстановка классов идёт по готовому HTML, легко задеть значение в таблице. → Перед правкой сохраняется исходный HTML каждого поля (как уже делалось в архивных изменениях: `*-before.html`), после правки сверяется текст без разметки. Спецификации `product-specifications`, `product-documentation` и `product-content-localization` остаются действующими и проверяются после.
- **Английская версия отстаёт.** Правки легко сделать только для `ru_language` и забыть про `en_language`. → Каждый товар правится парой полей сразу, проверка идёт с кукой `lang=en`.
- **Спрайты иконок у части товаров могут оказаться одинарными.** Тогда при наведении иконка «уедет» в пустоту. → При обходе товаров проверяется соотношение сторон загруженных иконок; для одинарных сдвиг отключается классом на обёртке.
- **Fancybox может использоваться в контенте.** Удаление библиотеки сломает такие места. → Удаление только после поиска `data-fancybox` по шаблонам и по содержимому полей.
- **Потеря позиций в поиске.** Редизайн меняет разметку всех страниц. → URL, заголовки H1, тексты и `alt` изображений сохраняются; структура заголовков на странице остаётся прежней по уровням.

## Migration Plan

1. Работа ведётся в отдельной ветке и в `main` не вливается до приёмки: пуш в `main` сразу выкладывает сайт. Локально `dist/` пересобирается для проверки, но не коммитится — его собирает раннер.
2. Слои SCSS и шаблоны правятся в порядке из Д12; после каждого слоя страницы просматриваются на ширинах 1440px и 390px рядом с макетом.
3. Контент 13 товаров правится после того, как стили вкладок готовы, — иначе не видно, что получается. Для каждого товара сохраняется исходный HTML полей.
4. Перед выкладкой: полный обход страниц на обоих языках, проверка действующих спецификаций (`catalog-visibility`, `homepage-promo-slider`, `product-specifications`, `product-documentation`, `product-content-localization`).
5. Перед выкладкой на текущий коммит `main` ставится аннотированная метка `pre-redesign`. Это точка, в которую возвращается весь редизайн разом.
6. Выкладка: влить ветку в `main` — дальше раннер соберёт тему и зальёт её сам. Сразу после этого проверить на сервере, что в `dist/` по одному файлу стилей и скриптов.
7. Приёмка на боевом сайте: снять скриншоты «после» для тех же страниц и ширин, что и «до», сверить попарно; пересобрать снимки содержимого вкладок и сверить текст без разметки с `content-before`. Расхождений в текстах, числах и ссылках быть не должно — меняется только оформление.

### Откат

Выкладка идёт из `main`, поэтому откат — это тоже коммит в `main`, после которого раннер сам вернёт сайт:

```bash
git revert -m 1 <коммит слияния> && git push origin main
```

Один коммит возвращает всю тему разом — шаблоны, стили, скрипты и сборку. Метка
`pre-redesign` показывает, каким было состояние до редизайна, и позволяет сверить
результат отката: `git diff pre-redesign main -- wp-app/` после отката должен быть пуст.

Контент товаров откатывается отдельно, из сохранённых `content-before/*.html`, —
правка контента живёт в базе, а не в репозитории, и обратным коммитом не снимается.

Редизайн их не касается; удалять ли их заодно — можно решить в конце.
- Добавлять ли опорные классы (Д9) в выпадающий список стилей редактора сразу или после того, как контент 13 товаров будет размечен вручную.
- Останется ли на главной один промо-баннер или редактор добавит ещё. На вёрстку не влияет — слайдер поддерживает оба случая.
